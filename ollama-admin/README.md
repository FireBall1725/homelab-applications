# ollama-admin

> Web UI for managing models on the external Ollama inference host

## Overview

Ollama Admin lists the models installed on an Ollama server, pulls new ones, deletes and copies them, unloads models from memory, and logs every request that passes through it. This chart deploys the Next.js app and its CloudNative-PG managed PostgreSQL cluster into `app-ai`, next to the [`ollama`](../ollama/) Service bridge.

It replaces remote-desktopping into the inference host to run `ollama pull`. Nothing is installed on that host; the app reaches it over the HTTP API on port 11434.

The container listens on `:3000`. Upstream ships a Dockerfile and a docker-compose file but no Helm chart, so this one is ours. It follows the `firebin-api` pattern: pinned image, CNPG cluster, SealedSecret for the session key.

## How it reaches Ollama

`DEFAULT_OLLAMA_URL` is `http://ollama:11434`, the Service that the [`ollama`](../ollama/) chart publishes in this namespace. That chart deploys no workload; it is a `Service` plus a hand-written `Endpoints` object pointing at the inference host on the LAN. Both charts must stay in `app-ai` for the bare service name to resolve.

Every call the UI makes is proxied through the app's own `/api/proxy` route rather than going straight to Ollama, which is where the request logging, per-IP rate limiting, and `oa-` API keys come from.

## Service links are disabled

`enableServiceLinks: false`. Kubernetes injects Docker-style link variables for every Service in a namespace, and `app-ai` contains a Service named `ollama`. Left on, the pod would start with `OLLAMA_PORT=tcp://<clusterIP>:11434` and `OLLAMA_SERVICE_HOST` set in its environment, inside an application whose entire job is talking to Ollama. [Spoolman](../spoolman/) hit the same trap with `SPOOLMAN_PORT`.

## Secrets

Uses [Sealed Secrets](../SECRETS.md) for sensitive values.

| Secret | Contents | Source |
|--------|----------|--------|
| `ollama-admin-nextauth` | `NEXTAUTH_SECRET` (NextAuth session signing key) | SealedSecret (`templates/sealed-secret-nextauth.yaml`) |
| `ollama-admin-db-app` | PostgreSQL DSN (`uri` key) | Auto-generated by CNPG operator |

`NEXTAUTH_SECRET` is `openssl rand -base64 32` sealed for `app-ai`. Keep it stable; changing it invalidates every session. To rotate:

```bash
openssl rand -base64 32 | tr -d '\n' > /tmp/ns
kubectl create secret generic ollama-admin-nextauth \
  --namespace=app-ai --from-file=NEXTAUTH_SECRET=/tmp/ns \
  --dry-run=client -o yaml | \
  kubeseal --controller-namespace kube-system --format yaml \
  > ollama-admin/templates/sealed-secret-nextauth.yaml
rm -f /tmp/ns
```

## Database

`DATABASE_URL` comes from the CNPG-generated `ollama-admin-db-app` secret. The DSN it emits starts with `postgresql://`, which is what `docker-entrypoint.sh` matches on to rewrite the Prisma provider from `sqlite` to `postgresql` before the app boots.

On the PostgreSQL path the entrypoint runs `prisma db push --skip-generate`, not `migrate deploy`. There is no migration history in this database; upstream schema changes get applied by diffing against the live schema on the next boot. The SQLite path is the one with real migrations.

## The GPU agent is not deployed

`GPU_AGENT_ENABLED` is `false` and stays that way. Upstream ships an optional Python sidecar on port 11435 for GPU telemetry, and on Apple Silicon it reports numbers that do not mean what the UI labels them. Reading `gpu-agent/main.py`:

- `temperature` is the literal value `-1`.
- `utilization` is `(active pages + wired pages) / total RAM`, so the GPU utilisation gauge is really a system memory gauge.
- `powerDraw` is only emitted on the NVIDIA code path. Apple gets no field at all.
- `memoryUsed` is whole-system RAM, not what Ollama or the GPU holds.

It also shells out to `system_profiler` and `vm_stat`, so it reads whatever machine it runs on. Deployed here it would report a Talos node's memory, not the inference host's. Running it natively on the Mac would report the right machine and still show `-1` for temperature.

Real per-model VRAM and which models are loaded come from Ollama's own `/api/ps` and show up in the UI without the agent.

## Notes

- PostgreSQL is provisioned via a `Cluster` CR managed by [CloudNative-PG](../cloudnative-pg/).
- Probes hit `GET /` on `:3000`; there is no dedicated health endpoint. The startup probe allows 60 failures at 5s because `prisma generate` and `prisma db push` run on every boot, and the first boot also waits on a cold CNPG cluster.
- `readOnlyRootFilesystem` is not set, on purpose. The entrypoint rewrites `prisma/schema.prisma` with `sed -i` and `prisma generate` writes `node_modules/.prisma`, so the root filesystem has to be writable.
- `runAsUser` and `runAsGroup` are `1001` to match the `nextjs:nodejs` user the image creates. The numeric UID is required: `runAsNonRoot: true` against the image's bare `USER nextjs` fails admission because Kubernetes cannot verify a username is non-root.
- `LOG_STORE_PROMPTS` is `false`, so request logs keep metadata and drop prompt and response bodies. Upstream defaults it to `true`.
- Upstream has no LICENSE file despite the README claiming MIT.
